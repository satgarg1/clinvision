## Pharmacy billing & inventory

Raised 2026-09-03: many small clinics dispense medicine on-site (a counter behind or next to reception) and today run a completely separate pharmacy package for it — a doctor/owner has to reconcile two disconnected systems for one patient visit. Scoped here, not started. Real new territory for this codebase: everything so far has billed a *service* (a consultation); this bills and tracks *physical goods a clinic owns and can run out of*, which is a different problem shape.

**Competitor research (mybillbook.in's pharmacy product, checked 2026-09-04)** — worth reading against a key difference: myBillBook sells to *standalone retail pharmacies, pharmacy chains, and wholesalers/distributors* as their own primary business; ClinVision's pharmacy feature is for *a clinic's own attached dispensing counter*, serving that clinic's own patients alongside a consultation, not a business selling medicine as its main line. Several of myBillBook's features exist specifically for that different customer and don't fit here — noted below so this isn't just copied wholesale:
  - **Already covered by what's scoped below**, same or equivalent: GST invoicing with HSN codes and item-wise tax breakup (schema section), batch + expiry tracking with FEFO (Milestone B), a pre-loaded medicine database (the ~500-item starter catalog, Milestone A), barcode scanning at checkout (Milestone C), low-stock alerts (Milestone C, called "reorder surfacing" there), purchase/stock-in recording (Milestone B), receipt printing (reuses `billing.html`'s existing layout, no change needed).
  - **Genuinely missing from the scope below, worth adding** — real reporting on the pharmacy data once it exists, not just billing+stock: fast/slow-moving medicine analysis, an expiring-stock-value report (what's sitting on the shelf about to become a write-off, in ₹, not just a count), and profit margin per medicine (purchase price vs. selling price, the actual margin a pharmacy counter runs on — genuinely new information a clinic doesn't have today even informally). Added to Milestone C below, alongside the H1 register — all three are the same "derive a report off data already being captured" shape.
  - **Considered and deliberately not adopted, given the different customer**: e-Way Bill generation (a legal requirement for *transporting* goods above a value threshold across state lines — a clinic dispensing to its own patients at the counter is a point-of-sale retail transaction, not goods movement, so this practically never applies here); a loyalty/rewards program (fits a retail pharmacy chain competing for walk-in customers, not a clinic's own existing patients); Tally export (a whole-app accounting-export feature if it's ever worth building, not pharmacy-specific — would apply to consultation billing too, so it doesn't belong only in this section); multi-godown/warehouse management (ClinVision is single-location per clinic today — see the "not decided yet" note below, this isn't new); wholesaler/distributor-facing bulk sale flows (not this product's customer at all).
  - **Worth a standing note, not an action item yet**: mandatory GST e-invoicing currently kicks in above a turnover threshold (periodically lowered by the government) — unlikely to affect a single clinic's *pharmacy* revenue specifically any time soon, but worth someone checking the current threshold if/when this ships rather than assuming it never applies.
  - **Already inherited for free from the rest of the app, not a new build**: role-based access (admin/staff/doctor roles already exist), multiple staff transacting concurrently (the existing Supabase-backed architecture already supports this), cloud storage/auto-sync (same), and patient-details capture (the existing `patients` table already holds name/phone/age/gender/address — a pharmacy sale just references the same record, not a second customer database).
  - **Overlaps an existing backlog item, not a separate build**: medicine refill reminders (myBillBook's own feature) would ride the same future notification pipeline as this file's existing "Real WhatsApp/SMS delivery" and "Patient recall reminders for recurring/chronic patients" items — once those ship, a refill reminder is one more trigger on that pipeline, not new infrastructure. WhatsApp bill delivery is the same story.

**The one thing this has to get right first: pharmacy billing only replaces the second software if it's the same app, not necessarily the same document.** Originally scoped as one merged invoice (consultation + medicine on the same `invoices` row) — **revised 2026-09-04, no real problem with 2 separate bills after pushback on this**. What actually caused the "2 softwares" pain wasn't 2 printed receipts, it was 2 disconnected systems: separate patient records, separate stock data, manual double entry, no shared view of what one patient paid today. If ClinVision generates *both* bills itself, from the same patient record, in the same session, that pain is gone regardless of whether 1 or 2 documents come out the other end.

  Two separate bills (a consultation invoice + a pharmacy invoice, same shape as `invoices` today, just tagged by type/reused twice) is arguably the *simpler* build too, and matches how a lot of real multi-service Indian clinics/hospitals already bill — pharmacy, lab, and consultation are commonly separate bills even within one facility. It also sidesteps a genuine tax wrinkle worth knowing regardless of which way this goes: a doctor's own consultation is GST-**exempt** healthcare service (Notification 12/2017, Entry 74), while dispensed medicine is a **taxable** goods sale (5/12/18% depending on the drug) — perfectly legal to mix exempt + taxable lines on one invoice (hospitals do it constantly), but keeping them on separate invoices makes each one's tax treatment unambiguous with zero extra logic.

  **Decided 2026-09-04: build 2 separate invoices**, not 1 merged one. Both still come from the same app/patient record.

  **Reversed 2026-09-05: `revenue.html`/Insights do NOT combine the two.** The original plan above called for both invoice types to roll up together into one reporting picture — built that way in the first pharmacy commit, then explicitly un-done once it was live: pharmacy invoices were leaking into Revenue's totals, Insights' charts, reception's own "already billed today" lookup, and the billing-numbering audit (which started reporting false gaps, since consultation and pharmacy invoices each keep their own separate number sequence sharing one table). `getInvoicesForDate`/`getInvoicesForDateRange`/`getOutstandingInvoices`/`get_billing_audit()` now all filter to `invoice_type = 'consultation'` explicitly. Pharmacy's own numbers live in `pharmacy.html`/`manage-medicines.html`'s stock ledger only, for now — a combined view (if wanted later) would need to be built as its own deliberate feature, not an accidental side effect of a shared table.

**Yes, real inventory tracking is required, not optional** (direct answer to "do we have to build inventory management too?") — a billing-only version (type in medicine names and prices, no stock) is a much smaller build, but it doesn't let a doctor actually drop their separate pharmacy software: they'd still need something tracking what's in stock, what's expiring, and what to reorder. That's the whole reason the second piece of software exists today. Skipping inventory ships half the value.

**Software side — new schema, in rough dependency order:**
- `medicines` — the clinic's own catalog: name, generic name, manufacturer, form (tablet/syrup/injection/etc.), strength (e.g. "500mg"), unit of sale (strip/bottle/piece), drug schedule (H/H1/X — none, or a controlled-substance flag; see the legal note below), default MRP, default selling price, GST rate, HSN code. Clinic-entered, not sourced from an external drug database — there's no free authoritative Indian equivalent to the US's NDC, and licensed pharma data feeds (IQVIA and similar) are a real recurring cost this doesn't need to take on to ship a first version. A CSV bulk-import for the initial catalog (rather than one-by-one entry) matters in practice — a real pharmacy counter can carry 200–2000+ SKUs.
- `medicine_batches` — Indian law requires a batch number + expiry date on a pharma sale invoice (Drugs and Cosmetics Rules), so stock can't be one plain quantity column on `medicines`; each batch needs its own quantity-remaining, expiry date, purchase price, and MRP (MRP can legitimately differ batch to batch). Deduction on sale should be FEFO (first-expiry-first-out), not FIFO — the standard pharmacy practice to minimize expired write-offs, and a real behavioral difference from how a generic e-commerce inventory model would default.
- `medicine_purchases` (stock coming in) — supplier name (plain text for v1, not a full supplier-master table — that's real added scope for later if reordering/supplier-comparison ever becomes its own feature), supplier invoice number, date, and line items (medicine, batch, quantity, purchase price) per purchase. Without this, stock only ever decreases in the system and silently diverges from the real shelf within days.
- Pharmacy sale line items — its own invoice (per the decision above), same line-item shape the existing `invoices` pattern already uses, not a new sales/orders table invented from scratch: medicine_id, batch_id (which batch was actually deducted — needed for a recall or an expiry dispute), quantity, unit price, tax. `batch_id` on the line item is what makes FEFO auditable after the fact, not just correct at the moment of sale.
- `stock_adjustments` — manual corrections (breakage, spillage, an expired batch written off, a physical count that doesn't match the system) — real inventory always drifts from a physical shelf count over time; without this there's no honest way to reconcile the two, only unexplained mismatches.
- **Schedule H1 register** (legal requirement, not a nice-to-have): H1 drugs (a defined list — certain antibiotics, psychotropics) must be sold only against a prescription and logged in a register with patient name, prescriber, drug, quantity, and date, retained for a set period. This can be a *derived* report/query off the sale line items above rather than a separate table, but only if `medicines.schedule` is captured accurately from day one — retrofitting it onto historical sales after the fact isn't possible.
- GST invoicing: the pharmacy invoice needs HSN codes and a proper tax breakdown (CGST+SGST or IGST) per line — a genuinely different shape from the consultation invoice's own (mostly GST-exempt) receipt, which is exactly why keeping them as 2 separate invoices (decided above) is the cleaner path rather than one document juggling both tax treatments.

**Hardware side — much lighter than "pharmacy software" might suggest:**
- **Barcode scanner (optional, but the realistic checkout speed win)**: a standard USB or Bluetooth barcode scanner needs zero special integration — these are all "keyboard wedge" devices that just type the scanned digits into whatever text field currently has focus, exactly like a fast typist would. A plain focused `<input>` at checkout is the entire integration; no driver, no browser API, no vendor SDK.
- **Receipt/invoice printing**: no new hardware need — `billing.html` already has a print-only receipt layout sized for A4 (styles.css's own "Billing receipt" block); the pharmacy invoice reuses that same print layout (just its own invoice number/line items/tax breakdown), not a separate thermal-receipt printer or a new print flow.
- **Barcode label printing** (a clinic generating its *own* labels for repackaged/split stock) is a real, separate hardware+software need (a thermal label printer, typically ZPL-driven) — most small pharmacies dispense using the manufacturer's own printed barcode/strip and never need this. Deferred; not part of a first version.
- Nothing here needs new server-side infrastructure — this is schema + frontend on the same static-site-plus-Supabase architecture the rest of the app already uses.

**Suggested milestones** (mirroring how the ABDM work was sequenced — ship the cheap, clearly-valuable slice first):
- **A** — `medicines` catalog + a single stock-quantity column (no batches yet) + dispensed items generating their own pharmacy invoice (separate from the consultation invoice, per the decision above). Gets pharmacy billing/stock working inside the same app fast; deliberately not yet expiry-safe.
  - **Decided 2026-09-04**: every new clinic's catalog ships pre-seeded with a starter list of roughly 500 common Indian medicines (name, common form/strength, a simple internal reference number, a default GST rate) instead of starting from a completely blank list — the clinic edits/adds/removes from there rather than typing 500 rows by hand on day one. This is a content deliverable ClinVision compiles itself, not a paid drug-database license (still true, see above) — worth being upfront that it needs real care in 2 places specifically: **Schedule H/H1/X classification** (legally meaningful — a wrong classification is a compliance issue, not just a data-quality one) and **MRP figures**, which drift over time and by brand/pack size, so the seed list should read to the clinic as an editable starting point, not authoritative live pricing. Building the actual 500-row list is real work for whenever this milestone starts, not something to draft inline in this file.
- **B** — `medicine_batches` + FEFO deduction + `medicine_purchases` (stock replenishment). This is the point real inventory accuracy exists, not just a stock counter that only ever goes down.
- **C** — low-stock/reorder surfacing, the Schedule H1 register report, barcode scanner support at checkout (the input-focus integration above), `stock_adjustments` for reconciliation, and pharmacy reporting (added after checking a competitor's own feature list, 2026-09-04): fast/slow-moving medicines, an expiring-stock-value report, and profit margin per medicine — all derived off sale/purchase data already captured by this point, same shape as the H1 register right next to them.
- **D (later, if ever)** — barcode label printing, supplier-master table + purchase-order workflow, OCR/import of a distributor's own purchase invoice instead of manual entry.

**Not decided yet:**
- Whether a dispensed item still requires an actual `doctor.html`-side prescription first, or reception/the pharmacy counter can sell over-the-counter items without one — likely both need to exist, but which one is built first isn't decided.
- Whether non-H1 medicines get any prescription-linkage at all, or only H1+ schedule drugs do.
- How a multi-location clinic (if that ever exists on this platform) would separate stock per location — not a problem today (every clinic on ClinVision today is single-location), just flagged so Milestone A's schema doesn't accidentally assume single-location forever.

## Qlinic subscription billing (Razorpay)

Scoped 2026-08-30, not started — this is Qlinic charging **clinics** for using Qlinic (the SaaS subscription), a completely different thing from `billing.html`/`billing-consultation.html`, which is a clinic billing **its own patients**. Today `clinics.subscription_status` (migration `053_clinic_subscription_status.sql`) is flipped by hand; this feature is what would make that real.

**The one hard rule this is scoped around: Qlinic's own servers/database must never see or store a raw card number, CVV, or full UPI-linked bank credential.** Every approach below routes actual payment-instrument capture through Razorpay's own hosted Checkout, and Qlinic only ever stores the *token* Razorpay hands back — this is both a PCI-DSS requirement and the only realistic path for a static-frontend app with no PCI-scoped infrastructure of its own.

**How saving a payment method actually works:**
1. Admin clicks "Add payment method" in the new Settings page below.
2. Frontend calls a new Edge Function (`razorpay-create-token-order`) that creates a Razorpay Customer (if one doesn't exist yet for this clinic) and a zero/token-amount order server-side, using the Razorpay secret key — which never reaches the browser.
3. Razorpay's own Checkout.js opens (hosted by Razorpay, not Qlinic) with `save=1`, collects the card or UPI details directly, and returns a `token_id`/payment method reference to the frontend.
4. Frontend hands that token to another Edge Function (`razorpay-save-payment-method`), which verifies it server-side against Razorpay's API and stores only the safe-to-keep parts in a new `clinic_payment_methods` table: Razorpay's `customer_id` and `token_id`, the card network + last 4 digits (or masked UPI VPA), and an `is_default`/`autopay_enabled` flag. No PAN, no CVV, ever, at any point, in Qlinic's own database.
5. Recurring charges (autopay) run entirely on Razorpay's side against that stored token, via Razorpay's Subscriptions API (cards) or UPI Autopay/e-mandate (UPI) — Qlinic's backend only reacts to Razorpay's webhooks (`payment.captured`, `subscription.charged`, `subscription.cancelled`, mandate revoked), which is what actually flips `clinics.subscription_status` automatically instead of by hand.

**New backend pieces needed** (same Supabase Edge Functions pattern already used for ABDM, since this static-frontend app has no other place to put server-side code):
- `razorpay-create-token-order` — creates/reuses the Razorpay Customer, returns an order for Checkout to open against.
- `razorpay-save-payment-method` — verifies the returned token server-side, writes the safe fields to `clinic_payment_methods`.
- `razorpay-webhook` — the one public endpoint Razorpay actually calls; validates Razorpay's webhook signature, updates `clinic_payment_methods.autopay_enabled` / `clinics.subscription_status` accordingly.
- `razorpay-remove-payment-method` — cancels the mandate/token on Razorpay's side first, then deletes the local row — never delete-then-cancel, which would leave an orphaned live mandate still capable of charging the clinic.
- Razorpay's key pair lives in Supabase secrets (`RAZORPAY_KEY_ID`/`RAZORPAY_KEY_SECRET`), same as the ABDM bridge credentials — never a database table.

**New UI, per the user's own direction**: a new card on the Settings hub grid, styled with a gradient (like the login page's own gradient pill) rather than the plain white cards the other settings tiles use — "Subscription & Billing" stands out visually as the one settings item that's actually about money, matching how it's treated with more weight than "Appearance" or "Display screen." Opens a new settings sub-page with:
- The current plan/subscription status (reusing `clinics.subscription_status` — active/trialing/suspended, same states `account-suspended.html` already gates on).
- A payment-method card (the "card for payments" — a visual card UI showing the masked card/UPI info, network logo, "Default" badge) once one exists, or an empty state with "Add payment method" when none does.
- Remove — calls `razorpay-remove-payment-method`, cancels on Razorpay's side first.
- An Autopay toggle — enable/disable recurring auto-charge without removing the saved method entirely.

**Explicitly not scoped/started yet**: any actual Razorpay account setup (business KYC, live API keys), the Edge Functions themselves, the `clinic_payment_methods` migration, or the Settings UI build. This is a scope to build from, not a partial build.
