This is a bigger thing than it might look: `display.html` (the waiting-room TV board) and `queue.html` (a patient's own live-status link) already ship a full English/Hindi toggle today, but it's bespoke and narrow — a hand-maintained dictionary of fixed UI strings plus a hand-written phonetic Latin-to-Devanagari transliterator for names/addresses (`toDevanagari`/`HI_WORD_DICT`/`phoneticToDevanagari` in both files), built specifically because those two screens are patient-facing and needed real Hindi rather than a rough machine pass. - **Post-visit rating of ClinVision itself (not the clinic) — internal product feedback only** (scoped 2026-08-31, re-scoped 2026-09-01) — **re-scoped from the original idea**: this used to be a patient rating *the clinic*, visible to the clinic on their own dashboard. Redirected to be about the ClinVision experience specifically (the queue/status-checking flow itself, not the medical visit), and the data belongs to ClinVision, not the clinic — no clinic admin page ever shows it. Two reasons for the pivot: (1) a clinic's own patient-satisfaction data is arguably the clinic's business to collect, not their software vendor's to insert itself into and hold — a bad "clinic" rating sitting in a system the clinic doesn't fully control is an awkward vendor relationship; (2) ClinVision, like any SaaS, genuinely needs its own product-feedback loop, and that's a cleaner, unambiguous thing to build for.

  **Where it lives, unchanged from the original scope**: `queue.html`'s already-built "visit complete" screen (`showDone()`/`#doneState`), only shown for a genuinely completed visit (`status === 'done'`) — not the no-show variant (`status === 'no_show'`), where there's no experience to rate. Same mechanic: 1–5 stars, tap-to-select, an optional free-text box underneath.

  **What actually changes:**
  - **The question itself** needs careful wording so it reads unambiguously as "how was using this to check your status" and never as "rate your doctor" — the two are easy to blur in a patient's head at exactly the moment they'd naturally still be thinking about their visit. Exact copy not settled; something like "How was checking your status today?" rather than anything using the word "clinic" or naming the doctor.
  - **Schema, deliberately named to signal it's internal**: a new table — `product_feedback` (not `visit_feedback`, on purpose, so the name itself doesn't imply it's about the visit) — `clinic_id`, `patient_id`, `rating` 1–5, `feedback_text` nullable, `submitted_at`. `clinic_id` is kept only for ClinVision's own internal segmentation (e.g. "is the experience worse for larger queues" or "any clinic-specific UX friction"), never surfaced to that clinic.
  - **RLS, the one genuinely unusual part of this table versus everything else in the schema**: no `select` policy for the `authenticated` role at all — every other table in this app has a `clinic_id = my_clinic_id()` read policy so a clinic can see its own data; this table deliberately has none, so a logged-in clinic admin querying through the normal app connection can't read it even by accident. Only reachable via the Supabase SQL Editor / service role (same superuser-bypasses-RLS access already used for the `supabase/checks/` reference queries).
  - **Insert path unchanged from the original scope**: a new insert-only RPC scoped to that one `patient_id` — same security-definer pattern as `get_queue_status` — so a patient can only ever submit for their own visit, never anyone else's, and it can't be used to spam ratings.
  - **Submitted-once guard, unchanged**: check for an existing row before showing the form again, so reopening the link after already rating shows a "thanks, already submitted" state instead of the form again.
  - **New EN/HI strings, unchanged**: same pattern as everything else in `queue.html`'s `STRINGS` object.
  - **Where ClinVision itself sees this — resolved, and it's not a new page.** The original scope's open question ("where does the clinic see this") is now moot since the clinic never does. ClinVision views it the same way subscription activation and the consultation-duration checks already work: a saved query in `supabase/checks/` (`avg(rating)` for the running product-rating number, plus a feed of recent `feedback_text` rows) run manually against Supabase — no new internal-only UI being built for this yet, the volumes don't need one.
  - **Not decided yet: whether to ask every single completed visit, or throttle it** (e.g. once per patient per N days) — asking about "the clinic" every visit was harmless, but a chronic patient rating the ClinVision *app* itself every single time they check their status could start to feel repetitive. New consideration introduced by this pivot, not present in the original scope.

  **Explicitly out of scope for now**: any in-app page (for ClinVision's own team or anyone else) to browse this data — direct SQL is enough at current volumes; a real internal dashboard is a later problem if this ever needs one.

- **Patient-facing queue details: "how's today going" + clearer window language** (raised/expanded 2026-09-01, real discussion behind this one) — `queue.html`'s "View queue details" modal currently shows three raw numbers (`windowBookedCount`/`windowArrivedCount`/`windowNotArrivedCount`: "Booked in this window", "Arrived & waiting", "Not yet arrived"), scoped to "now through your appointment." Two problems worked through, not just one:

  **Problem 1 — the window numbers are only meaningful once you're close to your slot.** A 5pm patient checking at 2pm sees "0 arrived" for a window that hasn't started yet, which reads as broken or alarming rather than just "too early to mean anything." Fix: the window grid is **conditional/de-emphasized far out, shown properly once close** — exact distance threshold not decided yet.

  **Problem 1b — the "already passed" case isn't just de-emphasis, it's a wrong label** (worked through 2026-09-01, live screenshot: a 10:20am slot, doctor delayed, viewed at 10:53am still shows "5 · Booked in this window"). Once a doctor is running behind, "now through your appointment" is negative, so the window has nothing left to anchor to — "Booked **in this window**" becomes genuinely ambiguous (booked before 10:20? around now? the patient can't tell what the number refers to). The fix isn't rewording the same number, it's **re-anchoring the boundary to the patient's own slot time once `now` has passed it, and naming that time out loud** rather than saying "window": "5 had appointments up to your 10:20 AM slot" / "arrived by then" / "haven't shown up" in place of "Booked in this window" / "Arrived & waiting" / "Not yet arrived". This state should also lean harder on the Problem-2 summary below (the delay reason/doctor status) since a bare "5 ahead of you" without *why* reads as more alarming exactly when the patient is already running into the delay themselves, not less.

  **Problem 2 — even close to your slot, the window alone can't explain why the queue looks stalled or unusually slow**, because it has no memory of anything before "now." That's what "how's today going" answers instead, and — worked through via edge cases — it needs to be a **persistent summary shown at every distance, not just a far-out fallback**: a stalled queue right when you expected movement is more alarming than the same thing hours early, and a doctor's whole-day pace (started late, running behind all day) is invisible to a window that only looks forward from now. Content, in rough order of how cheap each is (all reference the *same doctor* this patient is booked with, today only):
  - **Doctor's current status** — Available / On a break (since 3:40pm) / Attending an emergency. Already tracked (`doctors.status`) and already shown elsewhere on this page — just needs surfacing in this modal too. No new data.
  - **Current delay reason, if a real one was typed** — already tracked (`status_note`, already filtered through `isRealStatusReason` to drop auto-generated noise). No new data.
  - **First patient called-in time today** — "Started seeing patients at 9:05 AM." One new query (earliest `called_at` today for this doctor), no schema change. Answers the edge case where the doctor started late vs. started on time but is just slow — two very different situations the window grid can't distinguish.
  - **Booked so far vs. seen so far, today** — "18 booked so far, 14 seen." The core throughput/pace fact. One new same-day aggregation query, no schema change.
  - **No-shows finalized so far today** — a quiet signal the queue may be moving a little faster than the raw booked/seen numbers suggest. One new query, no schema change.
  - **Average consultation time today** — flagged, not decided: this is a plain descriptive fact about *today only* (not a cross-clinic-validated prediction of anything future), so it's arguably distinct from the wait-time-estimation item's gate below — but close enough to that boundary that it needs an explicit yes/no before building, not a quiet inclusion. Would read from `consultation_duration_seconds` (migration `057`, already collecting).
  - **Number of breaks/emergencies today + total time away** — genuinely does **not** exist yet, unlike everything above. The schema only stores the doctor's *current* status, overwritten on every change — there's no history of past status changes to count or sum. Needs a new `doctor_status_log` table (or similar), written on every status change rather than just overwriting the current row. Real new scope on its own, not a free addition like the rest of this list — worth having (a strong "today's been disrupted" signal) but should be sequenced separately if it turns out to be too much for a first pass.

  **Also folded in from the original scope:**
  - **"(including you)" on whichever window-grid box the viewing patient's own `status` falls into** (`booked` → "Not yet arrived", `waiting` → "Arrived & waiting") — so a patient isn't left guessing whether they're part of the number they're looking at.
  - **Friendlier "not yet arrived" wording** — a bare number invites "those people no-showed, so I've moved up," when in this market people mostly arrive late rather than actually not showing up. Something like "X haven't checked in yet (most people arrive a little late)" rather than a bare count.
  - **Plain-language sentences over raw stat-grid numbers** throughout — jargon like "window" isn't patient vocabulary.

  **Explicitly and permanently out of scope for this item**: anything resembling a time estimate or projection (an ETA, "your turn in ~20 min," "doctor is running fast today so you'll likely be early," etc.) — even the descriptive stats above (average time, seen-so-far) are facts about what already happened, never framed as a claim about what happens next. That stays behind the separate wait-time-estimation item's own explicit 6-months/10-clinics data gate.

## Qlinic subscription billing (Razorpay)

Scoped 2026-08-30, not started — this is Qlinic charging **clinics** for using Qlinic (the SaaS subscription), a completely different thing from `billing.html`/`billing-consultation.html`, which is a clinic billing **its own patients**. Today `clinics.subscription_status` (migration `053_clinic_subscription_status.sql`) is flipped by hand; this feature is what would make that real.

**The one hard rule this is scoped around: Qlinic's own servers/database must never see or store a raw card number, CVV, or full UPI-linked bank credential.** Every approach below routes actual payment-instrument capture through Razorpay's own hosted Checkout, and Qlinic only ever stores the *token* Razorpay hands back — this is both a PCI-DSS requirement and the only realistic path for a static-frontend app with no PCI-scoped infrastructure of its own.

**How saving a payment method actually works:**
1. Admin clicks "Add payment method" in the new Settings page below.
2. Frontend calls a new Edge Function (`razorpay-create-token-order`) that creates a Razorpay Customer (if one doesn't exist yet for this clinic) and a zero/token-amount order server-side, using the Razorpay secret key — which never reaches the browser.
3. Razorpay's own Checkout.js opens (hosted by Razorpay, not Qlinic) with `save=1`, collects the card or UPI details directly, and returns a `token_id`/payment method reference to the frontend.
4. Frontend hands that token to another Edge Function (`razorpay-save-payment-method`), which verifies it server-side against Razorpay's API and stores only the safe-to-keep parts in a new `clinic_payment_methods` table: Razorpay's `customer_id` and `token_id`, the card network + last 4 digits (or masked UPI VPA), and an `is_default`/`autopay_enabled` flag. No PAN, no CVV, ever, at any point, in Qlinic's own database.
5. Recurring charges (autopay) run entirely on Razorpay's side against that stored token, via Razorpay's Subscriptions API (cards) or UPI Autopay/e-mandate (UPI) — Qlinic's backend only reacts to Razorpay's webhooks (`payment.captured`, `subscription.charged`, `subscription.cancelled`, mandate revoked), which is what actually flips `clinics.subscription_status` automatically instead of by hand.

**New backend pieces needed** (same Supabase Edge Functions pattern already used for ABDM, since this static-frontend app has no other place to put server-side code):
- `razorpay-create-token-order` — creates/reuses the Razorpay Customer, returns an order for Checkout to open against.
- `razorpay-save-payment-method` — verifies the returned token server-side, writes the safe fields to `clinic_payment_methods`.
- `razorpay-webhook` — the one public endpoint Razorpay actually calls; validates Razorpay's webhook signature, updates `clinic_payment_methods.autopay_enabled` / `clinics.subscription_status` accordingly.
- `razorpay-remove-payment-method` — cancels the mandate/token on Razorpay's side first, then deletes the local row — never delete-then-cancel, which would leave an orphaned live mandate still capable of charging the clinic.
- Razorpay's key pair lives in Supabase secrets (`RAZORPAY_KEY_ID`/`RAZORPAY_KEY_SECRET`), same as the ABDM bridge credentials — never a database table.

**New UI, per the user's own direction**: a new card on the Settings hub grid, styled with a gradient (like the login page's own gradient pill) rather than the plain white cards the other settings tiles use — "Subscription & Billing" stands out visually as the one settings item that's actually about money, matching how it's treated with more weight than "Appearance" or "Display screen." Opens a new settings sub-page with:
- The current plan/subscription status (reusing `clinics.subscription_status` — active/trialing/suspended, same states `account-suspended.html` already gates on).
- A payment-method card (the "card for payments" — a visual card UI showing the masked card/UPI info, network logo, "Default" badge) once one exists, or an empty state with "Add payment method" when none does.
- Remove — calls `razorpay-remove-payment-method`, cancels on Razorpay's side first.
- An Autopay toggle — enable/disable recurring auto-charge without removing the saved method entirely.

**Explicitly not scoped/started yet**: any actual Razorpay account setup (business KYC, live API keys), the Edge Functions themselves, the `clinic_payment_methods` migration, or the Settings UI build. This is a scope to build from, not a partial build.
